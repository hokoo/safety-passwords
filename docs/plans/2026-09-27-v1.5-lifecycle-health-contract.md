# v1.5 lifecycle and schedule health contract (T0)

This note fixes the implementation contract for E1 T1–T3 in the [public-plugin lifecycle plan](2026-09-27-public-plugin-lifecycle-plan.md). It implements accepted G3: existing password checks continue during a setup failure, incomplete setup is never marked successful, an authorized administrator can see a safe status and retry, and automatic retries are limited. Carbon Fields remains the settings UI; its registration is not a prerequisite for lifecycle work. This note does not add a public API or require a persisted state machine.

## Context and derived state

Determine the loader from the actual including MU file, as `Activation::loadedByMustUsePlugin()` does today; do not infer it from hook timing or store an installation-mode flag. Determine topology with WordPress `is_multisite()`, the current network, and its main site. The four combinations—ordinary/single, ordinary/network, MU/single, MU/network—run the same initialization service. In multisite, all lifecycle options and the canonical cron event belong to the **current network's main site**; capability and history work covers only that network under the existing `UserScope` rules. A request for another network must not inspect or repair this network.

Initialization status is derived for the current code version:

| Status | Meaning |
| --- | --- |
| `pending` | The completed-version marker is absent or stale (or the MU completion marker is absent in MU mode), no valid lease is held, and no recorded failure is cooling down. First installation and a new version start here. |
| `running` | An unexpired initialization lease is held. A second request does no initialization work and does not report success. |
| `ready` | The existing completed-version marker equals `VERSION` and, in MU mode, the existing MU completion marker is present. The marker may be written only after capability, current-password history, and canonical schedule verification succeed and the worker still owns the lease. |
| `retryable error` | Initialization did not complete and a safe failure category and next automatic retry time were recorded. The marker remains absent or stale. The administrator may retry immediately through the existing protected repair action, subject to the lease. |

The failure record needs only category, attempt count, target version, and next retry timestamp in a private, non-autoload main-site option. Clear it on success, activation/deactivation, and version change; a previous-version record cannot delay a new version. A lock refusal is `running`, not a failure attempt. Expired leases are claimable by one worker; never display or persist the lease owner in diagnostics. If a forced repair of a ready installation fails, invalidate the completed-version marker before work as the current code does, so the status cannot remain falsely ready.

**Schedule health is independent of initialization status.** `healthy` requires the cheap main-site check plus a successful recent network normalization; `degraded` means the main event is missing, has the wrong recurrence, or normalization failed; `verification due` means the main check passes but the last successful full network normalization is older than 24 hours or absent. `repair in progress` may be shown while the lease is held. The UI must never infer schedule health solely from the version marker. The daily verification timestamp is private and per main site. This status describes scheduling, not whether WP-Cron has executed on time.

## Bootstrap, retries, and concurrency

On each fully bootstrapped WordPress load with this plugin and target database, run the lifecycle decision once, after roles are available; `wp_loaded` is the intended common point. Do not wait for `carbon_fields_fields_registered` or for the deferred activation event. The ordinary activation hook stays registered and keeps its current public name and deferred event for compatibility. On the first suitable subsequent request, the shared initializer must finish pending ordinary setup even when deferred cron has not fired, and clear the superseded one-shot event. MU and upgrades use the same route. Password policy consumers retain their Carbon Fields settings-loading order. WordPress loads that cannot reach this hook or a working database are outside the promise.

An initial `pending` attempt is immediate. After a failed attempt, delay automatic heavy retries by `min(5 minutes × 2^(attempt − 1), 1 hour)`; cap the stored attempt count at the value that reaches the one-hour ceiling. A request inside the cooldown may read status and perform the cheap schedule check, but does not traverse users or sites for initialization. A protected manual repair bypasses only the cooldown, never the lease, capability, POST, or nonce checks. An automatic or manual failure records one sanitized category and a new cooldown; success clears it. Do not create a global login or site lockout during failures: the existing password checks remain active.

Use the current atomic main-site option lease as the single writer guard for initialization and deep schedule repair. Acquire it before mutating, re-read markers after acquisition, and check ownership before marking success; release only if still the owner. The 900-second lease may be reclaimed after expiry. T1 must make the lease safe for its longest uninterrupted operation (renew it or prove that operation finishes within the lease); if it expires mid-work, the old worker cannot publish `ready`. Concurrent cron, bootstrap, CLI, and repair requests must converge through the same guard and idempotent operations. No second request may duplicate a live worker's history/capability traversal or reschedule a healthy event.

## Cost of schedule verification

Every suitable load may check only the current network main site's event (`wp_next_scheduled`/recurrence and a local event count, with no user or site traversal). A missing or malformed main event triggers repair at the next eligible load, subject to the lease and retry deadline; this is independent of `ready`. Preserve a correct event's timestamp. Under the lease, use `Cron::ensureEvent()` and `Cron::isNormalized()` for deep normalization on initialization, explicit repair, a detected main-site defect, and at most once per 24 hours while ready. This site traversal is confined to the current network and removes legacy subsite events, duplicates, and wrong recurrence. Record the successful verification time only after normalized state is confirmed. A failed deep pass remains due and uses the same bounded retry formula, tracked separately from initialization failures so that schedule failure cannot turn a verified initialization into `retryable error`. A healthy main event with stale deep verification is reported as `verification due`, not proven healthy. No full user-history traversal runs for a ready version just to check cron.

The daily interval bounds **frequency**, not the duration of a network scan. Large-installation resumable batching is the separate v2 F3 task. WP-Cron still needs a WordPress request to run; CI, WP-CLI, and an external cron service are optional operator tools, never prerequisites for installation or upgrade.

## Safe diagnostic categories

Show status only on the existing settings page to users passing `Settings::canManage()` and localize/escape all messages. Use a fixed allowlist such as `initialization busy`, `capability repair failed`, `history verification failed`, `schedule repair failed`, and `initialization failed` (fallback for an unclassified error). Show a retry time when cooling down. Map internal failures to these categories; never display raw exceptions, SQL errors, option values, lock owner, account details, or authentication material. The existing repair POST keeps capability and nonce verification before invoking forced initialization. Diagnostic writes must not log sensitive data or change password checks.

## Required transitions and acceptance evidence

| From and trigger | Next state and required behavior |
| --- | --- |
| No current marker or new `VERSION`; first suitable load | `pending → running → ready` on success, within that request. A deferred one-shot event may run concurrently but cannot repeat the work. |
| `pending`; another worker owns a valid lease | `running`; leave markers and schedule untouched, then re-evaluate on a later load. |
| `running`; worker fails or loses lease | `retryable error` if this worker still owns the failure record, otherwise re-evaluate the winner's result; never publish `ready` without verified work and ownership. |
| `retryable error`; load before deadline | Remain `retryable error`; no heavy traversal. Protected manual repair may attempt now if lease is free. |
| `retryable error`; load at/after deadline | One lease holder retries; success becomes `ready`, failure advances bounded cooldown. |
| `ready`; main schedule missing/malformed | Initialization remains `ready` while schedule is `degraded`; one lease holder repairs/normalizes without rewalking users. |
| `ready`; main event correct, deep verification due | Initialization remains `ready`; one lease holder normalizes this network, then schedule becomes `healthy` if verified. |
| Deactivation | Existing deactivation hook clears scheduled events and lifecycle markers in the current scope; no bootstrap is possible after the plugin stops loading. |

T1 evidence: on separate ordinary requests with deferred cron execution disabled and enabled, the first suitable load completes capability/history/schedule and clears pending; MU and upgrade paths still complete; concurrent entry does not duplicate work; activation/deactivation and the public hook remain intact. T2 evidence: deleting, duplicating, or changing the main event is repaired on a normal load in both loader modes; legacy subsite events are removed at a deep trigger, another network is unchanged, and a repeated healthy load preserves the event timestamp without a network walk. T3 evidence: the four initialization statuses and independent schedule health are visible to the correct administrator; failure and cooldown do not cause per-request heavy work; protected manual repair works during cooldown but is refused while leased; invalid nonce, method, and insufficient capability fail; messages disclose only fixed safe categories.

Sources: `plugin-dir/safety-passwords.php` (public hooks); `plugin-dir/src/Activation.php` (markers, deferred event, main-site switching, lease, history/capability checks); `plugin-dir/src/Cron.php` (network normalization); `plugin-dir/src/Settings.php` (repair form and permissions); `plugin-dir/src/UserScope.php` (network user scope). Current v1.5 code does **not** yet meet this contract; T1–T3 implement it.
