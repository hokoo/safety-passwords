# Draft PR: Complete password lifecycle and verify WordPress integration

An ordinary activation could leave the second setup phase unfinished, and must-use installations had no activation hook to set up history, capabilities and periodic checks. The password reminder could show a negative day count after expiry; an already initiated reset could be repeated by cron; string constants from deployment configuration could disagree with their settings display. This change completes those paths and adds an isolated WordPress integration runner.

## Resulting behavior

- **#7 — MU and activation lifecycle:** Ordinary activation schedules its deferred setup and completes history, capabilities and one periodic event on the next request. The supported root MU loader initializes after Carbon Fields is ready and retries interrupted work. In one-network multisite, checks cover all accounts, including unassigned accounts. In multi-network installations, each network's main-site event applies its policy only to accounts with site membership in that network, including inactive-site members; shared accounts have one global WordPress password. Network settings require `manage_network_options`.
- **Expiry and repeated reset:** Admin bar and own-profile reminders show explicit due, overdue or reset-required states without negative days. A persisted initiated-reset flag prevents a second cron reset and duplicate mail; a successful password change clears it through the existing path.
- **#8 — Constants:** Supported boolean values and whole-number strings use the same effective policy and settings indication. The existing `SAFETY_PASSWORDS_MIN_LEN` name remains authoritative.
- **#15 — Integration tests:** The disposable Compose runner exercises ordinary, MU and network lifecycle, cron and reset behavior, expiry boundaries, settings and constant profiles on PHP 7.4/WordPress 5.0, PHP 7.4/WordPress 6.8 and PHP 8.2/WordPress 6.8. Its final phase downloads the lock-pinned official Stream 4.0.0 archive and checks fallback, real connector registration, deferred and immediate persistence, and custom logger selection. The Stream fixture installs a temporary MU sanitizer before activation and permits only fixed synthetic records. The separate CI workflow runs the same runner.

## Review and operations notes

Ordinary activation still completes on a later request; administrators should allow that request before expecting initialized history and cron. Removing an MU loader physically does not invoke deactivation. The repository readme documents explicit scheduler cleanup and removal of the private MU completion marker before a later reinstall. Saved password history and settings are preserved. The Stream check uses a separate disposable database and volume; no fixture record carries an account identifier, IP address or authentication material.
