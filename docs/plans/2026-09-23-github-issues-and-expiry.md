## 2. Жалоба на отрицательные дни

**Причина отображения подтверждена исходниками и чистым PHP-расчётом.** Формула в `General.php:106,129,136` эквивалентна для нормальных timestamp:

`остаток = интервал − число полных прошедших суток`.

Нижняя граница отсутствует. При интервале 30 дней:

| Прошло полных суток | Отображаемый остаток |
| --- | ---: |
| 29 | 1 |
| 30 | 0 |
| 31 | −1 |
| 130 | −100 |

Формула используется в верхней панели и на странице собственного профиля. Она совпадает с HEAD: дефект существовал до локального lifecycle-рефакторинга.

Контекст, который объясняет непостоянное проявление:

- Периодическая проверка назначена `twicedaily`, первый запуск через пять минут (`Cron.php:12–19`). [WP-Cron зависит от обращений к сайту](https://developer.wordpress.org/plugins/cron/), поэтому расписание само по себе не гарантирует своевременное исполнение.
- В MU-режиме lifecycle через обычный activation hook не выполняется — это предмет [#7](https://github.com/hokoo/safety-passwords/issues/7). Текущая незавершённая активация даёт ещё один возможный источник отсутствующего cron. Наличие этих причин на проблемной установке не проверялось.
- `Controller::checkUsers()` использует `last_reset`, инициирует обязательный сброс и не сдвигает дату последней смены (`Controller.php:296–315`). UI не учитывает `rp_inited`, поэтому пока старый timestamp сохраняется и страница доступна, счётчик продолжает уходить вниз.
- При отсутствии/нуле `last_reset` UI подставляет текущее время (`General.php:95,124`), а cron при первом обнаружении сохраняет timestamp (`Controller.php:297–299`). Отсутствующее поле само по себе не объясняет минус.
- Расчёт использует `time()` и секунды суток, а не календарные даты часового пояса WordPress. Сокращение настроенного интервала ниже возраста пароля также делает результат отрицательным.
- Вход не сравнивает возраст пароля со сроком напрямую: он реагирует на флаги, выставляемые другими путями (`Controller.php:31–62`). Новую политику блокировки каждого запроса этим исправлением вводить не предлагается.

**Рекомендованное исправление T3:** единый расчёт для обеих поверхностей; до срока сохранять существующее округление, после достижения срока показывать понятный текст «Срок смены пароля наступил. Смените пароль», при инициированном сбросе — соответствующее состояние. Не выводить отрицательное число и не подменять исправление простым скрытием просрочки. Просмотр UI не должен менять `last_reset` или запускать сброс.

Отдельный связанный дефект для T4: `Controller.php:291` использует `true === get_user_meta(...rp_inited..., true)`, а в обработчике входа (`:43`) сравнивается `'1'`. Согласно [контракту get_user_meta](https://developer.wordpress.org/reference/functions/get_user_meta/), сохранённый boolean true возвращается строкой `'1'`. Чистый PHP подтверждает, что `true === '1'` ложно. Это даёт основание ожидать повторные сбросы/письма при повторном cron. На реальном WordPress здесь ещё не воспроизведено; не считать защиту от повторной обработки работающей без T4.

Уточнение пользователя: плагин установлен как **MU**, версия описана как «свежая», отрицательное число может быть значительно больше единицы по модулю. Точный номер версии и место отображения неизвестны. Большой минус полностью объясняется той же формулой: при интервале 30 дней и возрасте пароля 130 суток получится −100; это иллюстрация, а не измерение на проблемной установке.

MU-режим повышает приоритет гипотезы отсутствующего/неработающего cron из #7, но состояние расписания и фактические запуски на этой установке не проверены. Отрицательное число также не доказывает, что сброс вообще не инициировался: UI игнорирует его состояние. Поскольку при отсутствии `last_reset` используется текущее время, минус предполагает уже имеющееся старое значение даты, а не только факт свежей MU-установки. Следующая диагностика должна различить отсутствие события, отсутствие его выполнения и уже инициированный сброс; достаточно обезличенных результатов проверок, без значений пользовательских метаданных.

### E2. Управляемый массовый сброс (#10)

Решение пользователя: нужны **две отдельные кнопки**, а не выбор единственного режима для реализации:

| Кнопка (рабочее название) | Эффект |
| --- | --- |
| «Сбросить пароли и отправить письма» | Принудительный сброс сейчас и массовая отправка ссылок на установку нового пароля через WordPress reset API. |
| «Потребовать смену при следующем входе» | Мягкое требование сменить пароль при следующем входе, без массовой рассылки и немедленной замены пароля самой командой. |

Outcome: администратор может предсказуемо запустить любой из двух режимов смены пароля для согласованной группы пользователей.
Scope: T8–T10: оставшиеся решения об охвате/ошибках, backend обоих режимов, две кнопки, права, повторное выполнение, тесты и документация.

Success Criteria: обе кнопки имеют понятные разные последствия; немедленный режим выполняет сброс и рассылку, мягкий — смену при входе без рассылки; авторизованный запуск каждого режима работает; неавторизованный/CSRF/replay не вызывает лишней операции; частичный сбой отражён; независимый QA принят.
Dependencies: решение T8; для реализации принятый E1 и тестовый стенд.
Risks/Open Questions: объём пользователей; восстановление после ошибки доставки; повторные операции и переход между двумя режимами. Два режима, сетевой охват и исключение только инициатора уже выбраны. Мягкий режим действует при следующем входе; существующие активные сессии не завершаются самой массовой командой.
